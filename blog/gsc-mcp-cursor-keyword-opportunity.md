# How I Automated Keyword Opportunity Finding in Cursor using GSC + MCP (Free Workflow)

> 从「每周导三次 CSV」到「在 Cursor 里问一句话」：一个 `.cursorrules` + 一个免费 MCP 服务器，
> 把 Search Console 变成可以直接对话的关键词机会雷达。

---

## TL;DR

- 痛点：GSC 后台只能看聚合数据，想看「哪些词有展示没点击」必须导 CSV 到 Excel 手动排序。
- 解法：把**判断逻辑**写进 `.cursorrules`（自动过滤品牌词、算机会分），把**真实数据**交给 MCP 服务器（`gsc_opportunity_radar` / `gsc_inspect_url`）。
- 成本：0。MCP 服务器用 [GSC MCP Core](https://mcp.glq-api.asia) 的免费额度，不需要装爬虫、不需要买第三方 SEO 工具。
- 产物：一句「帮我扫一下 xxx.com 这 28 天的机会词」，直接拿到一张按预估可捡点击排序、且已经剔掉品牌词的表。

---

## 一、痛点：SEO 一半时间在当 CSV 搬运工

先说清楚我到底在烦什么。

Search Console 的「效果」报表是个不错的数据源，但它只解决「看」，不解决「判断」：

1. **聚合视角，找不到长尾机会。** 报表默认给你 Top 查询，而真正能捡的钱往往在「曝光 500、点击 3、排名 9.4」这种中间层。你得自己导 CSV、加筛选、按 `曝光量 × (目标CTR − 当前CTR)` 手算。
2. **品牌词永远混在里面。** 站点名、品牌错拼、`品牌名 + login` 这类导航词会把 CTR 均值拉高，让你误以为「这个位置的 CTR 已经不错了」，于是错过真正该改标题的词。
3. **上下文断裂。** CSV 在 Excel，竞品 SERP 在浏览器，内容大纲在 Notion，AI 在另一个窗口 —— 数据、判断、执行三件事各自为政。
4. **每次都要重来一遍。** 上周的筛选条件、上个月写的公式，换个窗口就忘了，于是又导一遍、又拖一遍。

如果只是「更快的 CSV」，那用脚本就够了。我真正想要的是：**一个知道我品牌词、懂 CTR 曲线、能自己算机会分、还会给出处方的 SEO 分析员，坐在编辑器里。**

这正是 Cursor + MCP 能做的事。

---

## 二、思路：判断归规则，数据归协议

我把这件事拆成两半，因为它们的「变化频率」完全不同：

| 层 | 放在哪 | 变化频率 | 为什么 |
| --- | --- | --- | --- |
| 判断逻辑（品牌词表、机会分公式、输出格式、红线） | `.cursorrules` | 低，一个季度改一次 | 纯文本，改完立刻生效，可版本控制 |
| 数据能力（GSC 查询、URL 收录检查） | MCP 服务器 | 不用改 | 协议标准化，换编辑器也能复用 |

关键在**顺序**：先写规则，再接数据。反过来做的结果通常是「AI 拿到一堆数字，然后开始编故事」。

还有一个反直觉的点：**别让 AI 自己猜关键词。** 直接问「给我一些 SEO 机会词」，模型会给你一堆听起来很专业、但和你的站完全无关的词。有了真实 GSC 数据之后，模型的工作从「发明」变成「筛选 + 排序 + 开处方」—— 这才是它擅长的部分。

## 三、核心：这份 `.cursorrules` 让我不再手动筛词

把下面全文存成项目根目录的 `.cursorrules`（Cursor 会自动读取；新版 Cursor 也支持放进 `.cursor/rules/`，见文末附录）。

它做了四件具体的事：

1. **强制先取数**：不调用 `gsc_opportunity_radar` 就不许开始分析，杜撰数字直接判为失败。
2. **自动过滤品牌词**：品牌词表 + 导航意图词 + 编辑距离兜底，剔掉的词还要列出来给我复核。
3. **算机会分**：在工具返回的预估点击上叠加意图权重和排名区间系数，输出可排序的优先级。
4. **固定输出格式**：结论 → 机会词表 → Top 3 处方 → 已剔除清单 → 下一步，不给我一坨散文。

~~~markdown
# Role: 资深 SEO 增长工程师（Google Search Console 方向）

你是我的 SEO 顾问。所有判断必须建立在真实 GSC 数据上，而不是「通用 SEO 建议」。
没有数据就停下来要数据，不要编。

## 0. 硬性约束（违反即失败）

- 禁止虚构任何数字：impressions / clicks / CTR / position 只能来自 MCP 工具返回值。
- 禁止把工具没返回过的关键词写进结论。
- 工具报错 / 401 / 429（配额用尽）时：原样复述错误信息，立即停止分析，给出下一步建议。
- 一次只分析一个 siteUrl。siteUrl 必须与 GSC 属性完全一致：
  `sc-domain:example.com` 或 `https://example.com/`，两者不通用。
- 输出语言：中文。关键词、代码、专有名词保持原文。

## 1. 取数流程（固定，不许跳步）

1. 调用 `gsc_opportunity_radar`，参数按下面的默认值：
   - `siteUrl`：用户给定；没给定就反问，禁止猜测域名。
   - `daysBack`：默认 28。GSC 有 1–3 天数据延迟，工具已自动把结束日期回退到「昨天」。
     想看趋势时，分别跑 28 天和 90 天做对比，不要凭感觉说「最近变差了」。
   - `minImpressions`：默认 100；日曝光很低的小站降到 30，否则样本全是噪声。
   - `maxPosition`：默认 20。
   - `topN`：25。多取一些留出过滤余量，品牌词会吃掉一部分。
2. 只有在需要确认「这个落地页到底收录了没」时，才调用 `gsc_inspect_url`。
   单次对话最多检查 3 个 URL —— URL Inspection API 每天约 200 次配额，别拿来刷。
3. 若 `opportunities` 为空：把 `minImpressions` 降到 10 再跑一次；仍为空就如实说
   「这个时间窗口没有可打的机会词」，不要用通用建议凑字数。

## 2. 品牌词过滤（自动执行，不用问我）

命中以下任一条件即剔除，并在最后单独列出：

1. query 包含品牌词表中的任一词（大小写不敏感，忽略空格与连字符）。
2. query 包含品牌域名主体（去掉 TLD 的部分），例如 `glq-api`。
3. query 是我维护的品牌常见错拼 / 拼音 / 缩写。
4. 导航意图：query 出现 `login`、`sign in`、`sign up`、`官方`、`官网`、`下载`、
   `app`、`客服`、`电话`、`价格表` 等，或与任一品牌词的编辑距离 ≤ 2。
5. 当前 CTR ≥ 该位置档位目标 CTR 的 1.5 倍 —— 典型的高 CTR 品牌词伪装信号。

品牌词表（我自己维护，新增子品牌 / 产品名就加一行）：

```text
BRAND_TERMS = [
  "brand",          # 品牌英文名
  "brandname",      # 品牌连写形式
  "品牌中文名",
  "产品名",
  "品牌常见错拼"
]
```

> 判不准时放进「待确认」区，不许擅自当成机会词。

## 3. 意图分类与机会分

给每个留下的 query 打标：

- `transactional`：购买、价格、优惠、替代品、`pricing`
- `commercial`：对比、`best`、`vs`、`review`、推荐、选型
- `informational`：`how`、`what`、`why`、教程、是什么、怎么用
- `navigational`：直接丢弃，不进评分

机会分（越大越优先）：

```text
score = estimatedClicks × intentWeight × positionMultiplier

estimatedClicks   = 工具返回的 incrementalClicks，不要自己再乘一遍
intentWeight      = transactional 1.20 | commercial 1.15 | informational 1.00
positionMultiplier = 位置 4–10  → 1.2   改标题就能吃到，最便宜
                     位置 11–20 → 1.0   需要补内容深度
                     位置 1–3   → 0.6   已是头部，收益在 CTR 而不在排名
```

评分只用于排序。表格里必须同时给出原始 `estimatedClicks`，方便我复核。

## 4. 输出格式（固定，不要自由发挥）

### 结论（≤ 2 句）
这一轮最值得先做的一件事，以及预计多拿多少次点击（明确标注是估算区间）。

### 机会词表（按 score 降序，最多 10 行）
| # | 关键词 | 位置 | 展示 | 当前 CTR | 目标 CTR | 预估可捡点击 | 意图 | 机会分 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

### Top 3 逐个开处方
每个词给 3 条**可执行**动作：
1. 标题改写：给出 2 个候选 `<title>`（含关键词，控制在 60 字符内）。
2. 页面改动：加什么段落 / 表格 / FAQ，放在页面什么位置。
3. 内链：从站内哪些页面加锚文本指向它，锚文本用什么词。

### 已剔除（品牌词 / 导航词）
一行一条：`query` → 剔除原因。让我能检查规则有没有误杀。

### 下一步（选一个）
- 深挖某个词的 SERP 竞品（我会贴 URL）
- 用 `gsc_inspect_url` 查某个落地页收录状态
- 换时间窗口复跑，做趋势对比

## 5. 质量红线

- 不许输出「多做高质量内容」「提升用户体验」这类无法执行的建议。
- 不许为了 CTR 建议标题党：标题承诺必须在正文兑现。
- 预估点击是方向性估算（基于分段 CTR 模型），必须标注不确定性，
  不能说成「保证涨 X 点击」。
- 同一批数据不要重复调工具，省配额（免费额度 50 次 / UTC 日）。
- 我给的品牌词表与工具数据冲突时，以品牌词表为准，并提醒我更新规则。
~~~

### 几条规则的设计理由（不是玄学）

- **为什么把 `topN` 设成 25 而不是 10？** 品牌词通常占曝光榜前列，工具返回的是「机会词」但还没按你的品牌定义洗过。多取一点，过滤完刚好剩 8–10 条。
- **为什么默认 28 天，而不是工具默认的 7 天？** 7 天窗口里单个关键词的曝光波动太大，容易把噪声当机会；28 天覆盖一个完整搜索周期，`estimatedClicks` 更稳。工具默认值确实是 7，规则里显式覆盖它，是为了每次分析口径一致。
- **为什么要 `positionMultiplier`？** 位置 9 的词改个标题就可能进前 5，位置 2 的词改标题收益有限 —— 同样的「预估点击」，落地成本完全不同。
- **为什么强制列出「已剔除」？** 过滤规则最大的风险是误杀。把剔除清单摊开，我一眼就能看出「这个词其实是新品牌线，不该删」。
- **为什么强调 siteUrl 两种写法不通用？** 这是新手最常踩的坑：`https://example.com/` 和 `sc-domain:example.com` 在 GSC 里是两个不同属性，传错直接查不到数据。

## 四、接上真实数据：60 秒配置

规则只解决「怎么判断」，还得有人把数据端上来。让 Cursor 通过浏览器去抓 GSC 后台是条死路（要登录态、有前端渲染、会封），所以我用了一个现成的免费 MCP 服务器：**GSC MCP Core**。

它提供两个工具，正好覆盖我 90% 的日常需求：

| 工具 | 干什么 | 关键参数 |
| --- | --- | --- |
| `gsc_opportunity_radar` | 扫「高曝光 + 低 CTR + 中段排名」的机会词，用分段 CTR 模型（1–3 名 28% / 4–6 名 12% / 7–10 名 5%）估算排名提升后的可捡点击，并给出 3 条处方 | `siteUrl`、`daysBack`(1–90)、`minImpressions`、`maxPosition`(1–50)、`topN` |
| `gsc_inspect_url` | 查单个 URL 的实时收录状态：`verdict`、`coverageState`、canonical、上次抓取时间、富媒体结果 | `siteUrl`、`inspectionUrl` |

### 三步接入

1. 打开 [mcp.glq-api.asia](https://mcp.glq-api.asia)，用 Google 账号登录 —— 授权范围是只读的 Search Console（`webmasters.readonly`），它不能改你的站点。
2. 点「Generate API Key」。Key 以 `gsc_live_` 开头，**只显示一次**（服务端只存哈希），当场复制。生成后页面还会给出一段写好 Key 的配置，点「Copy config」就能直接拿走 —— 内容和我下面这段一致。
3. 把下面的配置粘进 `~/.cursor/mcp.json`（用户级，所有项目都能用），或者项目里的 `.cursor/mcp.json`（跟着仓库走）：

```json
{
  "mcpServers": {
    "gsc-mcp": {
      "url": "https://mcp.glq-api.asia/api/mcp",
      "headers": {
        "Authorization": "Bearer gsc_live_你的Key粘在这里"
      }
    }
  }
}
```

保存后回 Cursor：`Customize → MCP`，看到 `gsc-mcp` 变成绿灯即可；如果没变，重启 Cursor 或从面板里 reload。

### 怎么确认真的连上了

在 Cursor 聊天框里输入这句（别问业务问题，先验证协议层）：

> 列出你可用的 GSC 工具，并把每个工具的必填参数和取值范围列出来。

正常情况下它会报出 `gsc_opportunity_radar` 和 `gsc_inspect_url` 及各自的 schema。**如果它开始「凭记忆」介绍 Google 官方 API，说明服务器没连上**，别急着往下用。

### 常见故障对照表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Missing API key` / `Invalid API key`（401） | 头部没写 `Authorization: Bearer ...`；或 Key 已被轮换（重新生成后旧 Key 立刻失效） | 检查 JSON；重新生成并替换 |
| `Daily limit of 50 requests reached`（429） | 免费额度按 UTC 自然日算 | 响应里带 `Retry-After`，指向下一个 UTC 零点；或者明天再来 |
| 调用成功但机会词为空 | 时间窗口太短、站点太新、或属性没有数据 | 把 `minImpressions` 降到 10，`daysBack` 拉到 90 再试 |
| 报 `siteUrl` 相关错误 | 属性写法不对：`https://example.com/` 和 `sc-domain:example.com` 是两个属性 | 回 GSC 后台复制属性的准确写法 |
| `Customize → MCP` 里根本看不到服务器 | JSON 少逗号 / 文件放错位置 / 没重启 | `Ctrl+Shift+U` 打开 Output，选 `MCP Logs` 看具体报错 |

> 安全边界：它用的是**你的** OAuth 凭据，MCP 端按 API Key 反查租户后注入该租户的 refresh token，不会跨用户复用凭据；免费额度也是按租户隔离的。

## 五、真正跑起来是什么样

配好之后，我的日常就三句话。

**1）例行扫描（每周一）**

> 用 gsc_opportunity_radar 扫 `https://glq-api.asia/` 最近 28 天，minImpressions 100，maxPosition 20，topN 25。按规则过滤品牌词，给我机会词表和 Top 3 处方。

**2）收录排查（改完内容之后）**

> 帮我检查这两个页面有没有被收录：`...` 、`...`，用 gsc_inspect_url。如果 verdict 不是 PASS，告诉我 coverageState 是什么、下一步改什么。

**3）趋势对比（月度复盘）**

> 分别跑 28 天和 90 天窗口，告诉我哪些机会词是「新出现的」，哪些是「一直在但一直没修」。

输出长这样（下面的数字是**虚构的示意数据**，只用来展示格式）：

| # | 关键词 | 位置 | 展示 | 当前 CTR | 目标 CTR | 预估可捡点击 | 意图 | 机会分 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | `vercel cron timezone` | 8.3 | 1,840 | 1.4% | 5% | 66 | informational | 79 |
| 2 | `supabase edge function timeout` | 5.8 | 920 | 4.2% | 12% | 71 | commercial | 98 |
| 3 | `mcp server vercel deploy` | 12.4 | 3,100 | 0.6% | 5% | 136 | commercial | 156 |

注意第 2 行：位置 5.8、CTR 4.2%，看着还行，但同档位（4–6 名）基准是 12% —— 这就是典型的「排名不差、标题不行」，改 `<title>` 是性价比最高的一刀。而第 3 行位置 12，得先补内容深度，预估点击虽大，落地成本也高，所以 `positionMultiplier` 把它压到 1.0。

**这就是手动做 Excel 永远做不到的地方**：不是算不出来，而是你每次都要重新搭一遍公式、重新定义一遍品牌词。

## 六、说清楚边界（不然就是软文）

这套流程好用，但它不是 Ahrefs 替代品。几个必须知道的限制：

1. **每次最多看 250 个 query。** 工具单次只拉 250 行 query 级数据（GSC 默认按表现从高到低返回）。所以它是「机会雷达」，不是「全量关键词库」。
2. **CTR 目标值是行业基准，不是你的站。** 1–3 名 28%、4–6 名 12%、7–10 名 5% 是分段估算模型，不同行业、有没有 AI Overview / 精选摘要 / 广告位，差异很大。所以「预估可捡点击」只能当**排序工具**，不能当 KPI 承诺 —— 工具输出里也自带这条免责说明。
3. **有 1–3 天数据延迟。** 结束日期会自动回退到「昨天」，所以「今天的排名」这种问题它答不准，也别问。
4. **免费额度是每天的。** 每个租户每天 50 次 MCP 调用（UTC 自然日重置）；Google 的 URL Inspection API 每天约 200 次。所以我把「扫一次 + 查 3 个页面」当一次完整流程，而不是每改一个字就重扫一遍。
5. **它不看竞品、不看外链。** 想要「对手拿了哪些词」，得自己贴 SERP 结果进来。

把这些写进规则里，AI 就不会替我吹牛 —— 这也是我坚持「数据归协议、判断归规则」的原因。

## 七、附录

### A. 新版 Cursor：改用 `.cursor/rules/*.mdc`

Cursor 正在用 Project Rules 替代 `.cursorrules`。把上面规则正文原样搬到 `.cursor/rules/seo-opportunity.mdc`，前面加四行 frontmatter 即可（`alwaysApply: true` 表示每个对话都生效；如果只想在写内容时生效，就把 `globs` 指向你的文章目录）：

```mdc
---
description: GSC 关键词机会分析：自动过滤品牌词 + 计算机会分
globs:
alwaysApply: true
---

（把第三节的规则正文整段粘在这里）
```

### B. 想自己托管？stdio 模式也能跑

不想用托管版（比如公司要求数据不出内网），可以把这个仓库 clone 下来自己跑，走本地 stdio：

```json
{
  "mcpServers": {
    "gsc-mcp-core": {
      "command": "node",
      "args": ["D:/code/gsc-mcp-core/src/index.js"],
      "env": {
        "GOOGLE_CLIENT_ID": "你的 client id",
        "GOOGLE_CLIENT_SECRET": "你的 client secret",
        "GOOGLE_REFRESH_TOKEN": "你的 refresh token"
      }
    }
  }
}
```

先 `npm install`，凭据也可以写在项目根的 `.env.local` 里（`src/gsc-client.js` 会读）。注意 stdio 模式是**单租户**的，只适合自己用；多账号/给团队用还是走远程 HTTP + API Key。
